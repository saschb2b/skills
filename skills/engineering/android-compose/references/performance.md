# Performance

**Verified 2026-06-15** against Compose BOM 2026.06.00, Kotlin 2.4.0 (Strong Skipping default-on). The principles are durable; profiling tool names move.

## Recomposition is the thing to control

Compose recomposes composables that read changed state. Performance work is about (1) reading state as late and as narrowly as possible, and (2) letting Compose skip composables whose inputs didn't change.

## Strong Skipping changes the old advice

**Strong Skipping is on by default since Kotlin 2.0.20.** A restartable composable is now skipped when its parameters are unchanged even if a parameter type is *unstable* (unstable params are compared by instance reference; stable params by `equals`). Consequences for how you write code:

- **Stop reflexively adding `remember`/`derivedStateOf`** to "fix" recomposition. Most lambdas and values no longer need manual memoization to enable skipping. Add memoization only where profiling shows a real, expensive recomposition.
- Strong Skipping auto-remembers lambdas, so you don't need to wrap every callback in `remember`.
- You still benefit from real stability: pass immutable data so skipping uses value equality (catches "same content, new instance") instead of instance equality.

This mirrors the React Compiler shift: the compiler handles the common case; manual memoization is the exception, not the default.

## Stability

A type is **stable** if Compose can trust that `equals` reflects all observable changes and that public properties don't mutate without notifying. Stable: primitives, `String`, function types, `@Immutable`/`@Stable`-annotated classes, and classes the compiler infers as stable.

- Mark model classes used as composable parameters `@Immutable` (deeply immutable) or `@Stable` (mutations notify Compose).
- `List`/`Map`/`Set` interfaces are treated as **unstable** (the runtime type could be mutable). For parameters, use `kotlinx.collections.immutable` (`ImmutableList`, `persistentListOf()`) or wrap in an `@Immutable` holder so value-equality skipping applies.

```kotlin
@Immutable
data class FeedUiState(val posts: ImmutableList<Post> = persistentListOf())
```

## Defer state reads with lambda modifiers

Reading state in a lambda passed to a modifier defers the read to the layout/draw phase, so changes skip recomposition entirely.

```kotlin
// BAD: reads offset in composition -> recomposes every frame of the animation
Box(Modifier.offset(x = animatedX))

// GOOD: lambda overload reads in the layout phase -> no recomposition
Box(Modifier.offset { IntOffset(animatedX.roundToPx(), 0) })

// Same idea: graphicsLayer { } for alpha/scale/translation animations
Box(Modifier.graphicsLayer { alpha = animatedAlpha })
```

Prefer the lambda overloads (`offset {}`, `graphicsLayer {}`, `drawBehind {}`) for frequently changing values.

## Lists

- Always supply a stable `key` to `items(...)` (see [compose.md](compose.md)).
- Don't put a `LazyColumn` inside a vertically scrolling `Column`; nest with a single scroll container or use the list's own `item`/`header` slots.
- Hoist `rememberLazyListState()` only if you read it; reading `firstVisibleItemIndex` directly in composition recomposes on every scroll, so wrap it in `derivedStateOf`.

## Measure, don't guess

- **Compose compiler reports/metrics** show which composables are skippable/restartable and which params are stable. Enable the metrics output in the Compose compiler Gradle options and read the generated reports to find unstable parameters.
- **Layout Inspector** in Android Studio shows live recomposition counts per composable; chase the ones recomposing far more than expected.
- **Baseline Profiles** (`androidx.benchmark` + a `baseline-prof.txt` generated by a Macrobenchmark test) precompile hot paths (startup, first scroll) so they run as compiled code on first launch. Generate and ship one for any production app; it is one of the largest startup/jank wins.
- **Macrobenchmark** measures startup time, frame timing (jank), and scrolling under a real device profile. Track regressions in CI.

## Other wins

- Avoid allocating in composition (no `LocalContext.current` work, no list building) on the hot path; hoist into `remember`.
- Use `remember(key)` for genuinely expensive derived values (parsing, sorting large lists), keyed on the inputs.
- Don't read `MaterialTheme`/`CompositionLocal`s in tight inner loops; read once and pass down.
